## 项目协作框架设计（讨论阶段，未实施）

用户设想：用 WorkBuddy + Godot + Obsidian 开发游戏，agent 团队分「设计 / 制作 / 审查」三角色，职责严格隔离（设计不落地、制作不改方案、审查不参与前两者）。用户是唯一决策者。

本轮产出的是**方案讨论**，项目目录当时为空，未创建任何文件/目录。用户明确要求方案满意后才实施。

### 已提出的框架 v0.1（待用户确认）

核心判断：难点不是"分三个角色"，而是三次交接；agent 无跨会话记忆，**文件就是消息总线**。

三条铁律：
1. 设计意图只存在于 vault；代码不硬编码设计（数值/文案/规则走数据文件）；vault 不写节点树。
2. 交接物必须可判定（可观测的验收标准，而非形容词）。
3. 谁产出谁举证（自检报告 / 审查证据）。

目录四层（单仓）：
- `vault/` 设计真源（Obsidian）：00-项目 / 10-设计 / 20-决策 / 30-验收
- `work/` 交接总线：tasks 四态目录（backlog/doing/review/done）+ reports + reviews + escalations
- `game/` Godot 项目：scenes / scripts / assets / tests
- `.workbuddy-ai/` + `docs/`：agents 角色提示词、skills、memory、技术决策 ADR

补漏：三角色缺"技术方案归属"，故引入第四类产物 **ADR**（制作写、设计读、审查质疑）。

工作流五态四门：待办 →(G1 规格可测)→ 规格就绪 →(G2 规格冻结/用户签字)→ 制作中 →(G3 自检通过)→ 待审 →(G4 AC 全绿)→ 已验收 →(用户实机)→ 完成。
异常路径：审查不通过→退回制作；规格不可实现/矛盾→升级给用户+设计。
关键机制：目录即状态、规格冻结+变更单、审查三结论、用户只在 G1/G4 介入。

Godot 风险点：.tscn 并发冲突（单场景单 agent）、project.godot 共享瓶颈、.import/.uid 入库而 .godot/ 忽略、审查需 headless 可运行、二进制资产 LFS 且单文件 <5MB。

建议先做 10 分钟垂直切片验证流水线，再扩规模。

### 待用户拍板
引擎版本与 2D/3D；游戏类型与体量；资产来源；是否长期单人开发。

## 游戏初设计讨论（第一轮，未落文档）

角色定位：我是本项目的**总设计师**，负责与用户讨论玩法/技术/架构；方案须用户同意后才能写入 `docs/设计/`；不负责制作，`docs/设计/` 之外一律只读。制作由用户另行派给制作 agent。

### 需求原文要点（docs/需求/最初设计.md）
修仙题材；资源生产与管理 + 角色实力提升为主要玩法；要求符合直觉、符合真实修仙；Godot 4.7.2；UI 草图三栏（左人物面板 / 中活动区最大 / 右 AE2 终端式物品管理，上网格下详情）。

### 用户已明确的判断
- 真正想做的是**剧情驱动的沉浸式修仙世界**，但因体量限制，现阶段重心放在**各玩法系统实现**上。
- 三栏草图是**暂定的 UI 外壳**，不是最终形态。
- 活动节奏：**前期单线程，境界解锁并行**。
- 寿元机制：**暂不讨论**（我建议设计成可插拔压力源，核心循环不依赖它）。
- 美术方向：待定，用户要求先说明我的美术能力再决定。

### 我提出的设计主张（待用户确认）
- 一句话定位：重生仙帝，用有限寿元在"修炼—采集—炼制—突破"生产链上做取舍，把荒废洞府经营成能渡劫飞升的道场。
- "仙帝归来"= 放置类的威望重置（转世重修），叙事与机制天然合一。
- 四条铁律：一人一时只做一事（并行须由分身/傀儡/弟子承担）；时间是唯一不可再生资源；突破必须失败；没有无输入的产出。
- 三层循环：秒-分（选活动/耗时耗材/产出/速率）、分-时（修为满/备齐条件/赌突破/境界提升）、时-天（扩建洞府/分工/自动化/渡劫转世）。
- 叙事主张：**剧情长在活动上，不长在关卡上**（活动挂事件池，第 N 次或满足条件触发事件卡）。第一版须提前留三个接口：世界状态 flags、事件池、统一条件表达式。
- 中间活动区必须是**可替换容器**，允许被全屏接管（对话/过场/突破演出）。
- 架构主线：表现层 / 模拟层（纯 GDScript、固定 tick、全局时钟、可 headless）/ 数据层（CSV·JSON→Resource，代码里不出现具体物品名）；UI 只发指令，模拟层只发信号。
- 第一版垂直切片建议：炼气一层→三层、3 个活动（打坐/采药/炼丹）、约 8 种物品、1 条生产链、1 次会失败的突破。

### 重要发现：本会话 AI 生图不可用
`ImageGen` 连续三次返回 `Image model [gpt-image-2.5-sunburst] route config not found`，与参数无关。**当前环境下无法生成位图**，所有基准图均为手写矢量。

### 矢量能力的边界（已验证）
- 强：UI 布局、图标、控件、图表 —— 一致性 100%，改一处全站生效。
- 中：写意场景 —— 靠 feTurbulence + feDisplacementMap 造墨块边缘，能做出"水墨海报"级的构图，但**做不到笔触的浓淡飞白**，需要几百行手写代码且不可复用。
- 弱：人物与生物 —— 只能做符号化的剪影/线稿，做不了表情、动作、立绘。

### 结论/建议（待用户确认）
把插画定位成中间区的**可替换背景层**：第一版用矢量场景占位，不阻塞开发；AI 生图恢复后再替换，不影响任何逻辑。这依赖"中间区是可替换容器"这条架构决定。

### 环境备注
用 `msedge --headless=new --screenshot=<绝对路径>` 可渲染 HTML/SVG 自检；**相对路径会写到别的目录**，必须用绝对路径。
