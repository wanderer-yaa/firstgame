# 协作约定

> 版本：v1.0　更新：2026-10-24
> 本文件定义本项目的角色与交接规则，**所有角色的 agent 都应读**。
> 共享记忆（`.workbuddy-ai/memory/MEMORY.md`）只放项目事实；**角色职责以本文件为准**。

---

## 0. 为什么要有这份文件

Agent 之间没有跨会话记忆，**文件就是消息总线**。

所以角色不靠"记得自己是谁"来维持，而靠两件事：

1. 所有 agent 读**同一份**约定（就是这份）
2. 每个 agent 的**配置**里写明它是哪个角色

这样即使三个 agent 互相看不见，也不会串角色。

---

## 1. 四个角色

| 角色 | 一句话 | 判断标准 |
|---|---|---|
| **设计** | 决定做什么、怎么算做对了 | 关心"这是不是我要的" |
| **制作** | 把它做出来，并证明做对了 | 关心"能不能跑" |
| **审查** | 独立核对"做对了没有" | 关心"证据够不够" |
| **用户** | 拍板、最终验收、仲裁 | — |

---

## 2. 设计

| 项 | 内容 |
|---|---|
| **输入** | 需求、用户反馈、审查报告 |
| **产出** | `docs/设计/` 下的规格书 |
| **做** | 出规格、定验收标准、判"是否符合设计意图"、补规格空白 |
| **不做** | 写代码、跑测试、改实现 |
| **关键约束** | 规格只写"错了会毁设计"的部分：A 类规则 + B 类数值 + 验收方式。C 类实现一律不写 |

---

## 3. 制作

| 项 | 内容 |
|---|---|
| **输入** | `docs/设计/` 下的规格书 |
| **产出** | `game/` 下的代码与资产 + 验收证据 |
| **做** | 实现、自检、产出证据、调 B 类数值 |
| **不做** | 改 A 类规则、改规格、替设计做决定 |
| **关键约束** | A 类改动必须回设计；B 类可调但要记录；C 类自己定不必报备；规格空白必须问，不许猜 |

---

## 4. 审查

| 项 | 内容 |
|---|---|
| **输入** | 规格书的验收标准 + 制作交出的证据 |
| **产出** | `docs/审查记录/` 下的验收报告 |
| **做** | 逐条验、核对证据、出结论（通过 / 不通过 / 需澄清） |
| **不做** | 参与设计、改代码、提"改进建议"（那是设计的活） |
| **关键约束** | **复核上下文必须与写代码的上下文分离**——同一个上下文自查等于没查 |

---

## 5. 交接规则

### 5.1 什么叫"交付完成"

**规格里每一条验收项都有证据，且证据可复现。**
口头"做完了"不算交付。

### 5.2 三种退回

| 情况 | 退给谁 | 例子 |
|---|---|---|
| 实现不符规格 | **制作** | 突破显示成了精确值 |
| 规格本身有问题（矛盾 / 不可实现 / 漏写） | **设计** | 规格要求"离线不推进时间"但又要求"离线也老化" |
| 规格与设计意图矛盾 | **用户** | 规格符合要求，但做出来不是用户想要的 |

### 5.3 不许越界的事

- 制作不能因为"实现困难"就改 A 类规则——那是设计的事
- 设计不能因为"想看看效果"就自己写代码——那是制作的事
- 审查不能因为"觉得这样更好"就提设计意见——那会让三方职责糊掉

---

## 6. 新建 agent 时怎么做

三步，缺一不可：

**① 在系统提示词里写明角色**

> 你是本项目的**制作** agent。先读 `docs/协作约定.md` 与 `.workbuddy-ai/memory/MEMORY.md`。

**② 告诉它当前任务**

> 执行 `docs/设计/M0-垂直切片.md`。

**③ 不要给它别的角色的职责**

它读到分工表就知道自己不该改规格、不该做设计判断。**你多给一句"顺便看看设计有没有问题"，它的边界就糊了。**

### 注意事项

- 共享记忆里的分工表是**中性**的，不写"我是谁"，所以任何 agent 读都不会误解
- 每个 agent 会话独立，别指望它记得别的 agent 说过什么——**只认文件**
- 三个 agent 同时跑时，`MEMORY.md` 只有设计能改，避免并发覆盖

## 7. 记忆写入规则

| 文件 | 谁能写 | 性质 |
|---|---|---|
| `.workbuddy-ai/memory/MEMORY.md` | 只有设计 | 当前事实 |
| `.workbuddy-ai/memory/YYYY-MM-DD.md` | 各角色追加 | 历史记录，**不是当前事实** |
| `docs/审查记录/` | 制作、审查 | 交付与验收留档 |

有冲突时，以 `MEMORY.md` 和 `docs/设计/` 下的规格为准。

## 8. 版本控制

### 8.1 一条铁律

> **一次提交只做一件事。**

原因：审查靠 diff。如果一次提交里既有"改了突破公式"又有"调了按钮颜色"，审查分不清哪个改动导致了问题——**大杂烩提交等于没提交**。

### 8.2 谁提交什么

| 角色 | 提交范围 | 说明 |
|---|---|---|
| 设计 | `docs/` | 规格与总纲 |
| 制作 | `game/` | 代码与资产 |
| 审查 | `docs/审查记录/` | 不提交代码 |

**同一时间只允许一个角色提交。** 两个 agent 同时 `git add` 会抢 index 锁。

### 8.3 提交信息

格式：`类型(范围): 说明`

```
feat(core): 时间推进与 tick
fix(save): 读档后突破结果被重算
docs(design): M0 规格按 A/B/C 分层
```

类型用 `feat` / `fix` / `docs` / `chore` / `test`。范围用系统名（`core`、`save`、`breakthrough`、`design`）。

### 8.4 分支与标签

| 项 | 规则 |
|---|---|
| `main` | **始终可运行**。跑不起来的不许留在 main |
| 标签 | 每个里程碑打一个（`m0`、`m1`） |
| 临时分支 | 大改动开 `exp/xxx`，验收通过才合并 |

单人项目不需要复杂分支模型。分支的唯一用途是"这次改动可能会砸"，其余直接在 main 上提交。

### 8.5 三条禁止

| 禁止 | 原因 |
|---|---|
| 提交引擎本体 `game/Godot_v4.7.2/` | 173M，且是工具不是内容 |
| 把 `.import` / `.uid` 加进 ignore | 它们是**项目源文件**，不是缓存。忽略会导致换机器后资源引用全断 |
| 忽略 `.godot/` 之外的 Godot 目录 | 只忽略 `.godot/` 和 `*.translation`，其余全提交 |

### 8.6 备份

本地 git 不防磁盘故障。建议推一份到私有远端（GitHub / Gitee 私有仓库）。

游戏项目丢仓库等于丢几个月，这一步不能省。
